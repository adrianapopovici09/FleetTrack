## Module reflection

### Three things I learned

1. **Async is about scalability, not speed.** A single async request isn't faster, but a waiting async request holds **no thread**. In M01-T2 the async endpoint served 100 concurrent users with ~9 threads from the first second. The blocking version needed ~100 threads, one per in-flight request, and froze for up to 13 s while the pool grew to that size.
2. **Cancellation only works if the token reaches the I/O.** In M01-T3, without the token, the Postgres query ran its full 10 s after the client had left. With the token passed down, `pg_stat_activity` showed the query cancelled as soon as the client disconnected. Our own 2 s timeout came back as a `504`, distinct from a client abort. CA2016 already fails the build when a token isn't forwarded.
3. **Allocation-free code mostly saves GC work, not time per call.** In M01-T4 the span parser allocated 40 B instead of 264 B (6.6× less), but was only ~21 % faster, because the parsing itself dominates. The win is Gen0 collections per 1,000 calls (0.0629 → 0.0095), which is what matters at ingest rates.

### One surprise

**A thread-pool minimum of 200 didn't make 400 users "a bit slower". It took the server down completely for ~3 minutes** (details below). I expected the slow ramp-up to come back above 200 threads. I didn't expect zero completed requests, a dead `/ping` and refused connections until the pool reached ~400 threads.

### One open question

How do you find sync-over-async in a large existing codebase **before** it freezes production? The candidates are analyzers (they only catch some patterns), load tests in CI (they need realistic concurrency) and runtime alerts on thread count and queue length (they catch it, but only in production). Which combination catches it earliest, for what cost?

## M01-T7: `SetMinThreads` as a band-aid

### What I did

I added `ThreadPool.SetMinThreads(200, 200)` to the M01-T2 lab, behind a flag so the T2 behaviour stays the default (`dotnet run -c Release --project labs/M01-T2-starvation -- --min-threads 200`; the app logs the return value and `GetMinThreads`). Then I reran the blocking endpoint `/slow-sync` with k6 for 30 s, restarting the API before each run:

- **Run A:** 100 virtual users (VUs), the same load as T2.
- **Run B:** 400 VUs (`k6 run --vus 400 …`).

Caveat: Visual Studio had recreated `Properties/launchSettings.json`, so both runs used the Development environment, as the first T2 runs did. The effect is small here (no `appsettings.Development.json`, and the app sets its own URL); the file has been removed again.

**Prediction:** run A would look like the async endpoint. Run B would need ~400 threads (400 VUs × 0.5 s blocking each, Little's law), so above 200 the slow ramp-up and starvation would come back.

### What I observed

| `/slow-sync` | 100 VUs | 400 VUs |
| --- | --- | --- |
| T2, no band-aid | 42–113 req/s · p95 0.5–5.1 s · max 12–13 s · ~100 threads | — |
| **T7, minimum 200** | **5,900 requests, 194.4 req/s · p95 519 ms · max 648 ms**; thread count not captured | **Total freeze for ~3 min**; `/ping` timed out; connections refused; recovered at **~400 threads** |
| Async (T2) | 5,900 requests, 194.0 req/s · p95 521 ms · ~9 threads | — |

Run B, sampled from the API process while it was frozen (OS threads, so slightly more than the pool's own count):

```
time      threads  CLOSE_WAIT  /ping
13:44:13    321       402      timeout     ← CPU flat at ~2.4 s total: doing nothing
13:44:56    370       402      timeout
13:45:06    388         3      timeout     ← threads ≈ 400: the backlog starts to drain
13:45:26    415         5      timeout
13:45:35    422         0      200         ← responsive again
```

The ~400 connections in `CLOSE_WAIT` were requests k6 had already given up on: the server processed them after the clients were gone.

### What would happen in production

Run A is the dangerous one, because it **looks like a fix**. Graphs are green, latency matches async, and the ticket gets closed. The real behaviour shows up later:

1. **Traffic grows,** or one instance drops out of the load balancer and the others take its share. The concurrency per instance passes the minimum.
2. **Or a dependency slows down.** The database goes from 500 ms to 2 s, so each request holds its thread 4× longer, and the same traffic suddenly needs 4× the threads.
3. Either way, **the instance freezes completely**, as in run B. To the load balancer it looks dead: health checks time out and connections are refused. The load balancer removes it, so its traffic moves to the other instances, which freeze in turn. A slow dependency becomes a full outage.
4. When the cause goes away, each instance needs **minutes** to grow enough threads to recover, and it spends them processing requests whose clients have already left.

### Why

**`SetMinThreads` only changes how many threads the pool creates *without delay*.** Below the minimum, a thread is added the moment work waits; above it, the pool adds threads slowly. With blocking code, Little's law says **threads needed = requests per second × seconds each request blocks**. A fixed minimum covers one load at one latency. Run A was exactly that case (100 concurrent requests, minimum 200). In run B the need (~400) was above the minimum, so the original starvation came back.

**Why a total freeze, not just slowness:** `Task.Delay(500).Wait()` blocks the thread until a timer callback completes the task, and that callback also needs a **thread-pool thread**. It sits in the queue behind hundreds of waiting requests. Every new thread the pool adds takes the next request and blocks too, so the callbacks that would release everyone never run. Nothing completes until there are enough threads for every request at once. Kestrel also needs pool threads to accept connections, which is why new connections were refused.

**It's a band-aid because it hides the cause:** the thread count looks flat and healthy until the day load or latency moves past the setting, and that day is usually when a dependency is already in trouble. Async doesn't have this cliff: waiting requests hold no thread, whatever the load or latency.

**When raising the minimum is legitimate:**
- blocking code I can't change yet (a sync-only SDK or driver)
- a known, bounded burst (a scheduled job firing 150 parallel calls)
- keeping production stable during a sync-to-async migration
- an emergency mitigation while the real fix is being released

In every case it's done **deliberately**:
- **Sized** with Little's law plus headroom, not a round number.
- **Monitored:** thread count vs the minimum, queue length, and dependency latency.
- **Set in configuration** (`ThreadPoolMinThreads` in the `.csproj` / `runtimeconfig.json`), not code.
- **Tracked:** a ticket and a date to remove it.

### The fix / the rule I'll follow

Async all the way down. Until that's possible, contain the blocking part instead of feeding it threads: a bulkhead (`SemaphoreSlim.WaitAsync` sized for the dependency) and load shedding (ASP.NET Core's concurrency limiter, fast `503`s). Raising the thread-pool minimum is a sized, monitored, temporary mitigation, never the fix.

## Team guidelines: async, cancellation and DI

### Rule 1: Never block on async code in a request path

- **Rule:** no `.Result`, `.Wait()` or `.GetAwaiter().GetResult()` on a `Task` in code that serves requests or runs on the thread pool. Don't wrap sync calls in `Task.Run` to make them "async" either.
- **Why:** each blocked request holds a thread-pool thread. Under load the pool starves. We measured a 13 s freeze at 100 users, and a total ~3-minute outage at 400 users even with `SetMinThreads(200, 200)` (M01-T2, M01-T7). `Task.Run` moves the blocking to another pool thread; it doesn't remove it.
- ❌ `var vehicle = repository.GetAsync(id).Result;`
- ✅ `var vehicle = await repository.GetAsync(id, ct);`
- **Exception:** a library that only offers sync methods. Isolate it behind a bulkhead (`SemaphoreSlim`) with a ticket to replace it. Never "fix" it with a thread-pool minimum alone.
- **Enforced by:** code review. CA1849 flags calling a blocking method when an async one exists, inside async methods. Alerts on thread-pool queue length > 0 for 30 s catch what gets through.

### Rule 2: Accept a `CancellationToken` and pass it all the way to the I/O

- **Rule:** every async method that does I/O takes a `CancellationToken` as its last parameter and passes it to every call that accepts one, down to the database and HTTP calls. Endpoints use the token ASP.NET Core provides (it fires when the client disconnects).
- **Why:** without it, work continues after the client has left. In M01-T3 a Postgres query ran its full 10 s after the client disconnected. Under load, that's capacity spent on answers nobody reads.
- ❌ `await db.Shipments.ToListAsync();`
- ✅ `await db.Shipments.ToListAsync(ct);`
- **Exception:** work that must finish once started, even if the caller leaves (for example writing the outbox row after the business change is committed). Pass `CancellationToken.None` **deliberately**, with a comment saying why.
- **Enforced by:** **CA2016** at `warning`, which fails our build (`TreatWarningsAsErrors`), as M01-T3 showed.

### Rule 3: Every outbound call has an explicit deadline

- **Rule:** calls to a database or another service run under a timeout: a linked token (`CancellationTokenSource.CreateLinkedTokenSource(ct)` + `CancelAfter(...)`). Our own timeout is reported as a `504`, a client abort is not reported as an error.
- **Why:** without a deadline, a slow dependency holds our resources for as long as it likes. That's how a slow database becomes our outage (M01-T7 production timeline). In M01-T3 the linked 2 s timeout cut a 10 s query and returned `504`.
- ❌ `await client.GetPositionAsync(id, ct);`
- ✅ `using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct); cts.CancelAfter(TimeSpan.FromSeconds(2)); await client.GetPositionAsync(id, cts.Token);`
- **Exception:** long-running background jobs, which get their deadline per unit of work rather than per call.
- **Enforced by:** code review, until a resilience pipeline makes timeouts a default (later modules).

### Rule 4: A service may only depend on services that live as long or longer, and the container checks it everywhere

- **Rule:** a singleton never takes a scoped or transient dependency in its constructor. Scope validation (`ValidateScopes` + `ValidateOnBuild`) is on in every environment, or a test builds the real container with both on.
- **Why:** a captured scoped service is shared by every request. In M01-T5 the captured `TenantContext` outlived its scope and was never disposed. With a `DbContext` that means "second operation started on this context" errors under load; with the current tenant it means one customer's data served to another. `WebApplication.CreateBuilder` turns validation on **only in Development**, so the bug ships silently.
- ❌ `services.AddSingleton<ReportService>();` where `ReportService(AppDbContext db)`
- ✅ register `ReportService` as scoped; or, for a true singleton, take `IDbContextFactory<AppDbContext>` / `IServiceScopeFactory` (rule 5)
- **Exception:** none for the rule. Validation can stay off in production for startup time **only if** a test runs the real container with it on.
- **Enforced by:** a test that builds the app's container with `ValidateScopes` and `ValidateOnBuild` on (the M01-T5 lab pattern). Note that `ValidateOnBuild` can't see inside factory lambdas.

### Rule 5: Background work creates one scope per unit of work and sets the tenant on it

- **Rule:** a `BackgroundService` (or any singleton) that needs scoped services creates **one scope per message or job** with `IServiceScopeFactory.CreateAsyncScope()`, sets the tenant on that scope **from the message itself**, and disposes the scope when the unit of work ends. Request-time code never creates its own scope.
- **Why:** a scope created once in the constructor is a captive dependency in disguise. A scope created inside request-time code holds a **fresh** `TenantContext` with no tenant, not the request's one (M01-T5): either everything fails, or a missing tenant filter returns every customer's data.
- ❌ `var db = _scopeFactory.CreateScope().ServiceProvider.GetRequiredService<AppDbContext>();` in a constructor, or inside a request handler
- ✅
  ```csharp
  await foreach (var message in channel.Reader.ReadAllAsync(stoppingToken))
  {
      await using var scope = scopeFactory.CreateAsyncScope();
      scope.ServiceProvider.GetRequiredService<TenantContext>().TenantId = message.TenantId;
      await scope.ServiceProvider.GetRequiredService<TelemetryHandler>().HandleAsync(message, stoppingToken);
  }
  ```
- **Exception:** none.
- **Enforced by:** code review and an integration test per background worker that checks two messages from different tenants are handled with their own tenant.
