# M05 answers — Modular monolith

1. **Layer vs module.** A layer groups code by technical role (data access, application logic) across *all* features. A module groups by business capability and owns everything for it, end to end (API, logic, data). Layers don't prevent coupling: any class in `Application` can use any other, every feature change touches every layer, and nothing stops feature A from using feature B's tables or services. Boundaries come from ownership and visibility, not from technical tiers.
2. **Finding contexts.** Listen for the same word meaning different things to different people ("shipment" to sales = a contract with a price; to dispatch = a load to plan), for different owners/teams/decision-makers, for different rates of change and different lifecycles. Walk an end-to-end story and mark where the language, data or rules change.
3. **Module owns its tables.** One writer per table keeps invariants enforceable and lets a module change its schema without breaking others. Shared tables are hidden coupling: a column change breaks unknown consumers, transactions span modules, and you can never extract the module. It also makes ownership and review clear.
4. **Module A needs B's data every request.** (a) Synchronous in-process call via B's contract: simple, always fresh, but couples availability/latency (fine in-process, costly once distributed). (b) A local copy kept up to date via B's events (event-carried state transfer): fast and independent, but eventually consistent, with more storage and code. (c) Rethink the boundary: maybe the data or behaviour belongs in A, or A and B are one context. Also: a composed read model at the API/UI level.
5. **Shared kernel.** A small set of code/models shared by several contexts by agreement (ids, `Money`, `TenantId`, base types). Every change to it affects every module and needs coordination, so it becomes a coupling hub and a bottleneck. Keep it to stable primitives, never business logic.
6. **Two DbContexts in one service.** The Shipments module reaches directly into Dispatch's persistence: it bypasses Dispatch's rules and invariants, couples to its schema, and creates a cross-module transaction. Fix: call Dispatch through `IDispatchApi` (its contract) or react to/publish events; Dispatch's `DbContext` stays `internal` to Dispatch (enforced by an architecture test).
7. **Slice duplication.** Acceptable when slices only *look* similar but change for different reasons (different use cases evolve independently): premature abstraction couples them. Extract when there's a real shared *concept* or rule (domain logic → aggregate/value object), or truly technical cross-cutting code (validation pipeline, paging helper), usually after the third occurrence.
8. **Extractable module.** Owns its data (no shared tables/joins); communicates through explicit contracts and preferably async events; no cross-module transactions; no reliance on in-process shared state (static caches, shared DbContext); its own config and registration; tests that run independently.
9. **Modular monolith vs microservices.** For: one deployable (simple ops, debugging, transactions), cheap refactoring of boundaries while the domain is still being learned, and a small team. Flip it when: parts need very different scaling/availability or technology, several autonomous teams need independent release cadences, or compliance/isolation requires a separate deployment.
10. **Two teams, one repo.** Assign module ownership (CODEOWNERS on module folders); a team changes another module only through its contract and with review. Architecture tests enforce boundaries. Contract versioning rules for module APIs/events. Each module's tests run independently; a trunk-based CI with fast feedback; feature flags so unfinished work doesn't block releases; ADRs for cross-module decisions; a shared kernel kept tiny with explicit owners.
