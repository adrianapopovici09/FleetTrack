# M00 answers — Foundations & guardrails

> Grade yourself 0 (missed), 1 (partly), 2 (complete, with the trade-off). An answer earns 2 only if it covers *why* and *when not*.

1. **Build.props vs Packages.props.** `Directory.Build.props` injects MSBuild properties/items into every project below it (nullable, analyzers, warnings-as-errors). `Directory.Packages.props` enables Central Package Management: it holds `<PackageVersion>` entries, and projects reference packages *without* versions. One configures the build; the other governs dependency versions.
2. **SDK selection.** `latestFeature` allows any SDK with the same major.minor (10.0) and a feature band ≥ 100, choosing the highest. `10.0.300` qualifies and is used. `11.0.100` is never chosen because the major version differs. If no 10.0 SDK existed, the build would fail.
3. **Testcontainers vs InMemory.** InMemory isn't a relational database: it ignores constraints (unique/FK), transactions, SQL translation (a LINQ query that can't translate works in InMemory but throws on Postgres), concurrency tokens, case sensitivity/collations and `timestamptz` behaviour. Testcontainers runs the real engine, so tests fail where production would.
4. **Liveness vs readiness.** Liveness asks "is the process healthy, or should it be restarted?" and checks only in-process state. Readiness asks "can it serve traffic right now?" and includes dependencies like the database. If liveness checks the DB, a DB blip makes the orchestrator restart *every* instance at once: a self-inflicted outage and restart storm, with no benefit since a restart doesn't fix the DB.
5. **Config precedence.** Later providers override earlier ones. The default order is appsettings.json → appsettings.{Env}.json → user-secrets (Development) → environment variables → command line, so the env var wins. `__` is the cross-platform separator for nesting (`:` isn't allowed in env var names on all platforms): `ConnectionStrings__FleetTrack` = `ConnectionStrings:FleetTrack`.
6. **Architecture tests vs review.** Reviews are inconsistent, scale badly, and miss transitive or subtle violations (a reference added in a 2,000-line PR). Tests are automatic, cheap, run on every PR, and document the rules as executable code. Reviewers then spend their attention on design rather than policing. Code review is still needed for things tests can't express.
7. **depends_on.** Plain `depends_on` only orders container *start*; it doesn't wait for Postgres to accept connections. Fixes: a `healthcheck` on Postgres + `depends_on: postgres: condition: service_healthy`; and make the app resilient anyway (retry on startup / readiness probes), because in production dependencies come and go.
8. **TreatWarningsAsErrors on legacy code.** Thousands of existing warnings block every build. Gradual introduction: enable it for new projects only; use `WarningsAsErrors` for a curated list of rules; set a baseline (fix one category at a time, or `<NoWarn>` temporarily with a ticket); use `.editorconfig` severities per rule; ratchet up in CI.
9. **Vulnerable packages.** It scans the *resolved* graph, including transitive packages, at build time, and can fail CI deterministically. Dependabot alerts are asynchronous notifications that people ignore; they don't block a merge unless you wire them as required checks, and they can lag behind.
10. **Legacy guardrails, in order.** (1) CI that builds and runs existing tests on every PR, required for merge: a safety net before changing anything. (2) Reproducible builds and dependency hygiene: SDK pinning, CPM, vulnerability scanning. (3) Analyzers/warnings as a ratchet (no *new* warnings) plus a few architecture tests for the most important dependency rules. Explain why: visibility before enforcement, and small wins that earn trust.
