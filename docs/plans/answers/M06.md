# M06 answers — Messaging & reliability

1. **Dual write / outbox.** Writing to the DB and publishing to the broker are two separate systems with no shared transaction. A crash between them leaves state changed with no event (or an event with no state, if you publish first). The outbox writes the message into an outbox table *in the same DB transaction*; a relay publishes it later and marks it sent, giving atomicity between state and message. It does **not** prevent duplicates (the relay can publish and crash before marking sent), so consumers must still be idempotent. It doesn't guarantee ordering across instances, and it adds latency and table maintenance.
2. **Exactly-once myth.** Acks can be lost: a consumer processes a message, then crashes or the network drops before the ack, so the broker must redeliver or risk losing it. You can't distinguish "processed but ack lost" from "not processed". Build **at-least-once delivery + idempotent processing** = effectively-once *effects*.
3. **Commands vs events.** A command is imperative (`AssignVehicle`), sent to exactly one logical handler that owns the decision, and may be rejected. An event is past tense (`VehicleAssigned`), published by the owner of the fact, with zero or more subscribers that can't reject it. The sender of a command depends on the receiver; the publisher of an event doesn't know its subscribers.
4. **Idempotent consumers (best first).** (a) Naturally idempotent operations: set state rather than increment, upserts, conditional updates (`UPDATE ... WHERE status = 'Booked'`). (b) Dedupe by message id in an inbox table, in the same transaction as the effect. (c) Business keys/unique constraints that reject duplicates (e.g. one planning entry per shipment). Avoid "check then act" without a constraint.
5. **SKIP LOCKED.** Multiple relay instances or threads can poll concurrently. `FOR UPDATE` locks the claimed rows; `SKIP LOCKED` makes other pollers skip them instead of waiting. You get parallel relays without double-claiming and without lock contention/blocking.
6. **Save then publish.** Commit succeeds, then the publish fails or the process crashes: the event is lost, Dispatch never plans, and the system is silently inconsistent. If you reversed the order (publish then commit) and the commit failed, consumers would act on a non-existent shipment. A transient publish failure with a retry inside the request leads to slow requests/timeouts and possible duplicates. → outbox.
7. **RabbitMQ removal.** With manual ack, a message is removed when the consumer **acks** it. If the consumer crashes or the channel closes before acking, the message is requeued and redelivered (with `redelivered=true`), possibly to another consumer. That's why processing must be idempotent. With auto-ack, it's removed on delivery and lost on a crash.
8. **Ordered per shipment with 4 consumers.** Partition by key: consistent-hash exchange or N queues routed by `hash(shipmentId) % N`, one consumer per queue (ordering per partition). Or Wolverine/Service Bus sessions keyed by shipment id. Or design consumers to tolerate disorder (version numbers, ignore stale events, state-machine guards), which is often the most robust option.
9. **Kafka vs RabbitMQ.** Kafka: a durable replayable log, very high throughput, partition-ordered streams, multiple independent consumers re-reading history (telemetry streams, analytics, event sourcing feeds). RabbitMQ: flexible routing, per-message acks, low latency, simple work queues and commands, delays/DLX. For FleetTrack's business events at modest volume, RabbitMQ/Service Bus is simpler. Kafka is justified if telemetry volume or replay/analytics needs grow large.
10. **Reliable webhooks.** Store a delivery record (outbox) on the event. A dispatcher worker POSTs with an HMAC signature + timestamp + delivery id (receiver dedupe). Exponential backoff with jitter over hours/days; per-subscriber circuit breaker and concurrency limits; after max attempts, mark failed and alert; a delivery log + replay endpoint; subscribers verify signatures and respond 2xx fast (process async). Plus a polling fallback API.
