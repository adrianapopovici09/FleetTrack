# M08 answers — Real-time telemetry

1. **gRPC for ingest.** Pros: compact binary protobuf (bandwidth/battery), HTTP/2 multiplexing, streaming (one long-lived connection for many points), strongly typed contracts with codegen for many languages, deadlines. Cons: browsers need gRPC-Web, some L7 load balancers/proxies need HTTP/2 end to end (long-lived streams also unbalance load), it's harder to debug than JSON/curl (use grpcurl), and very constrained devices may prefer MQTT.
2. **Streaming vs unary batch on flaky networks.** A stream avoids per-request overhead and gives low latency, but when the connection drops you must reconnect and know what was acknowledged (needs per-batch acks/sequence numbers); long streams also pin to one server. Unary batches are simple, retryable, stateless and balance well, at the cost of a little more overhead and latency. Common answer: unary batches with idempotency keys for unreliable devices; streaming for stable, high-rate links.
3. **Unbounded channel.** Items queue without limit, memory grows until GC pressure and OOM, and latency grows unboundedly (the data is stale anyway). There's no backpressure signal to producers. Bounded full modes: `Wait` (the producer awaits → backpressure to the gRPC stream/client), `DropOldest`, `DropNewest`, `DropWrite`. You can also reject with an error so the client retries later.
4. **One row per ping, unpartitioned.** The table and indexes grow to billions of rows: B-tree index maintenance slows inserts, index size exceeds memory, vacuum/autovacuum struggles with huge tables, retention via `DELETE` is massively expensive (bloat, WAL), and queries over recent data still touch giant indexes. Partitioning keeps working sets small, and retention becomes `DROP TABLE partition`.
5. **BRIN on recorded_at.** Telemetry is mostly appended in time order, so physical block ranges correlate with time and min/max per range prunes well, with a tiny index and cheap inserts. It fails for columns whose values are scattered across blocks (device_id, status) or heavily updated tables. Late data reduces its effectiveness slightly.
6. **Out-of-order/duplicates.** Identity = `(device_id, recorded_at)` (or a device sequence number) with a unique constraint → `ON CONFLICT DO NOTHING` for dedupe. Store by event time, not arrival time; accept late data within a window (writes go to the correct partition; reject or quarantine data older than retention or too far in the future given clock skew). "Latest position" logic compares `recorded_at`, never arrival order. Geofence evaluation must handle a late point that predates the current state (ignore it for state transitions, or re-evaluate a window).
7. **Clients.All per ping.** (1) A cross-tenant data leak: everyone gets everyone's positions. (2) Massive fan-out: every client gets every vehicle at full ping rate, so bandwidth/CPU explode and slow clients cause server-side buffering. (3) No coalescing/throttling (the UI only needs the latest per second) and it's done inline on the ingest path, coupling ingest throughput to push. Use groups per tenant/shipment, coalesce, push asynchronously.
8. **Geofence hysteresis.** GPS jitter (±10–30 m) near a boundary flips the point in/out repeatedly, producing a storm of enter/exit events and flapping shipment state. Require N consecutive points or a minimum dwell time inside/outside, or use a buffer zone (enter at the polygon, exit at polygon + 50 m).
9. **Backplane.** Needed when running more than one SignalR server instance: a message sent on server A must reach clients connected to server B (groups span servers). The cost: every message goes through Redis (or Azure SignalR Service): extra latency, Redis throughput as a bottleneck, and messages broadcast to all servers. Alternatives: sticky sessions + sharded groups, or Azure SignalR Service.
10. **Estimate.** Writes: 5,000/5 s = **1,000 points/s** (~86M/day). At ~100 bytes/row incl. index ≈ 8.6 GB/day ≈ **~260 GB/month** raw (compression/aggregation or shorter retention matter). Push: viewers mostly watch subsets; worst case 10,000 viewers × updates for vehicles in view. With coalescing to 1 update/s per visible vehicle and ~20 vehicles per viewer ≈ 200k msgs/s worst case, hence groups, viewport filtering and throttling. Biggest risks: storage growth/retention cost, and push fan-out/backplane throughput (also ingest bursts after connectivity outages).
