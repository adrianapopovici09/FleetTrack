# M04 answers — Domain modelling

1. **Entity vs value object.** An entity has identity that persists through changes (same shipment even if the address changes). A value object is defined only by its values: immutable, interchangeable when equal. Entities: `Shipment`, `Vehicle`, `Driver`, `Customer`. Value objects: `Address`, `Money`, `Weight`, `TrackingNumber`, `TimeWindow`.
2. **Reference by id.** Navigation properties across aggregates create a mutable object graph: code can modify another aggregate through it, breaking that aggregate's invariants and its transaction boundary. They encourage huge loads and lazy-loading surprises, and they couple persistence models. Ids keep aggregates independently loadable, lockable, and later movable into another module/service.
3. **Shipment + Vehicle assignment.** Prefer **two transactions with eventual consistency** (aggregate rule: one aggregate per transaction). Shipment records the assignment and raises `VehicleAssigned`; the Vehicle aggregate reacts (reserve, or reject → compensate). A single transaction is acceptable if both live in the same module/DB, contention is low *and* the business truly needs atomicity. Name that trade-off explicitly. A saga (M07) handles a reservation failure.
4. **After commit.** If handlers run before commit and the transaction then rolls back, they've acted on facts that never happened (emails sent, messages published, other aggregates changed). After commit, events describe true facts. (For cross-process delivery you also need the outbox, because the process may crash between commit and dispatch.)
5. **Public settable List.** Anyone can replace the list, add or remove stops without updating totals, break sequence ordering/contiguity, add stops to a delivered/cancelled shipment, add duplicates, or set it to null. The aggregate can't enforce any rule on its children.
6. **When exceptions still fit.** Truly unexpected or exceptional situations: programmer errors/invariant violations that should never happen (guard clauses), infrastructure failures (DB down, timeouts), corrupted state, cancellation. Also inside constructors of value objects, where you can't return a Result without a factory. Results are for *expected* business outcomes the caller should handle.
7. **Time in tests.** Inject `TimeProvider` into the aggregate method or handler (`shipment.MarkPickedUp(timeProvider.GetUtcNow())`, or pass the provider). In tests use `FakeTimeProvider` (`Microsoft.Extensions.TimeProvider.Testing`) and `Advance(TimeSpan.FromHours(49))`. Deterministic and instant.
8. **Anemic is fine** for CRUD-ish data with no invariants spanning fields or children: reference data, settings, lookup tables, simple admin screens, reporting read models. Forcing DDD there adds ceremony without protecting anything.
9. **Money.** `double` is binary floating point: 0.1 + 0.2 ≠ 0.3, and rounding errors accumulate across charge lines. `decimal` is base-10 exact for currency amounts. Rounding must be explicit (banker's vs away-from-zero, at line vs total level) because it's a business/legal rule. Currency must travel with the amount, so you can never add EUR to USD silently; conversion is an explicit operation with a rate and date.
10. **Split delivery.** Options: (a) `Shipment` gains `Consignment`/`Delivery` children, each with its own items/quantities and status, and the shipment status is derived ("partially delivered"); invariant: delivered quantities ≤ booked. (b) Split into two shipments linked by a parent/reference, when they become independent movements (different vehicles/billing). Discuss which invariants must hold atomically and who bills what. Prefer (a) if delivery is one commercial agreement.
