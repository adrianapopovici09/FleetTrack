# M09 answers — From modules to services

1. **Triggers.** Legitimate: independent scaling profile (Tracking ingest vs a CRUD UI); failure isolation/blast radius; different team ownership with its own release cadence; different technology/storage/runtime needs; compliance/data-residency isolation; very different availability targets. Bad reasons: "microservices are modern/CV-driven", "the code is messy" (a service boundary doesn't fix bad code, it distributes it), "to make the team move faster" without autonomous teams, copying big tech.
2. **DB per service.** Gains: the service owns its schema and can change it freely, there's no hidden coupling via shared tables, it scales and chooses storage independently, and failures are isolated. You lose: cross-service joins and ACID transactions (replaced by eventual consistency, sagas, read models), simple reporting (now needs a data platform/composed views), referential integrity across services, and some operational simplicity (more databases to run, back up and monitor).
3. **Event-carried state vs querying.** Local copy via events: low latency, works when the owner is down, no runtime coupling, but data is eventually consistent (stale for a moment), duplicates storage, needs backfill/replay, and couples to event schemas. Querying the owner: always fresh, one source of truth, no copies, but couples availability and latency (A down if B down), adds network hops and load on the owner, and needs resilience. Choose by freshness need and the dependency's criticality.
4. **Availability.** 0.999 × 0.999 × 0.999 ≈ **99.7%** (~26 h downtime/year vs ~8.8 h for one service), and that's before network failures. Every synchronous dependency multiplies unavailability. So prefer async integration, design graceful degradation/fallbacks, and keep critical paths free of sync chains.
5. **Distributed monolith.** Services that are separately deployed but tightly coupled: they must be deployed together, they share databases, they call each other in long synchronous chains, a change requires coordinated releases, one failure cascades through everything. Symptoms: release trains, lockstep versioning, chatty calls, incidents spanning many services, "we can't deploy X without Y". You get all the costs of distribution with none of the benefits.
6. **Zero-downtime data migration.** (1) The new service owns a new DB; create the schema. (2) Backfill historical data (export/import or replay events). (3) Keep it in sync while the monolith still writes: events from the monolith (outbox) or CDC (Debezium/logical replication). (4) Verify (reconciliation counts/checksums). (5) Switch reads to the new service behind a gateway/feature flag. (6) Switch writes (the new service becomes the owner; the monolith consumes its events if it still needs data). (7) Remove the old tables after a safe period. Keep a rollback plan at each step.
7. **No deadline/fallback.** If Tracking is slow, the shipment page hangs until the default gRPC/HTTP timeout (or forever). Threads and connections pile up, and the slow dependency cascades into the monolith (latency, pool exhaustion, timeouts for unrelated requests). If Tracking is down, the whole page errors even though position is a non-critical field. Add a deadline, the request's cancellation token, resilience (limited retries with jitter, circuit breaker), and a fallback ("position unavailable").
8. **Gateway.** A single entry point: routing, hiding internal topology and moves (strangler), TLS termination, authentication/token validation, rate limiting, CORS, request/response headers, sometimes response aggregation (BFF). It must not become a place with business logic or orchestration ("smart pipes"), a deployment bottleneck owned by one team, or a single point of failure without redundancy.
9. **Contract compatibility.** Versioned contracts in a package/schema registry; additive-only changes (new optional fields), never rename/remove/change type without a new version; tolerant readers that ignore unknown fields; consumer-driven contract tests (Pact) or schema snapshot tests in the producer's CI; run old and new versions in parallel during migration; deprecate with telemetry on who still uses v1.
10. **40 services, release train.** Diagnosis: a distributed monolith (coupled deploys, likely shared DBs/sync chains, missing contract discipline, poor observability). Plan: map dependencies and coupling from traces; establish contract versioning + contract tests so services can deploy independently; break sync chains with events/caching; add distributed tracing, SLOs and on-call ownership per service; consider **merging** services that always change together (fewer, bigger services or a modular monolith); move to independent CD per service with feature flags; measure deployment frequency, change failure rate and MTTR.
