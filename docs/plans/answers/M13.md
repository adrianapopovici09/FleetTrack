# M13 answers — Cloud, delivery & Aspire

1. **ACA vs AKS vs App Service.** Container Apps: containerised microservices/APIs/workers with event-driven scaling (KEDA), scale-to-zero and revisions, no cluster management. The default for small/medium teams. AKS: full Kubernetes control (custom operators, service mesh, complex networking, many workloads, multi-tenant clusters); needs platform/ops expertise and costs more. App Service: simple web apps/APIs, PaaS with slots, easiest for a few apps, less suited to many services and event-driven workers.
2. **Build once, promote.** The artifact tested in staging is byte-for-byte what runs in production: no "works in test, different build in prod" drift, reproducible and auditable (image digest), faster pipelines. Environment differences come only from configuration.
3. **GitHub → Azure without secrets.** OIDC workload identity federation: GitHub issues a short-lived OIDC token for the workflow run (with claims like repo, branch, environment); Azure AD trusts GitHub's issuer via a federated credential on an app registration/managed identity with a subject filter; `azure/login` exchanges the token for an Azure access token. No long-lived secret is stored.
4. **Backward-compatible migrations.** During a rolling/revision deploy, old and new app versions run against the same database simultaneously, and a rollback runs the old version against the migrated schema. So each schema change must work with both. Expand/contract: expand (add new nullable column/table, dual-write), migrate/backfill data, switch reads to the new structure, stop writing the old one, then contract (drop old) in a later release.
5. **Migrations as a pipeline step.** With N replicas starting, `Migrate()` at startup races (concurrent migrations, locks, partial failure), slows and blocks startup/health checks, requires the app to have DDL permissions (least privilege violated), makes failures appear as crashing pods, and ties the migration to the deploy timing with no review gate. A separate step (bundle/script) runs once, with elevated credentials, can be reviewed/approved, and failures stop the deploy cleanly.
6. **Managed identity.** It removes secrets (passwords, connection strings, keys) from config and their rotation/leak risk. Azure gives the app an identity; the app gets tokens via `DefaultAzureCredential`/`ManagedIdentityCredential`, and RBAC grants it rights (Key Vault Secrets User, Service Bus Data Sender, Postgres Entra auth). The SDK fetches tokens automatically, so there's nothing to store.
7. **Revisions.** An immutable snapshot of a container app's template (image + config). New deploys create new revisions; in multiple-revision mode you split traffic (e.g. 90/10 canary), test via revision-specific URLs, then shift to 100%, or roll back by sending traffic back to the previous revision instantly.
8. **Migrate() with 3 replicas.** Three instances race to apply migrations simultaneously (lock contention, duplicate-object errors, a partially applied migration). Startup is delayed past health-check timeouts so pods get restarted mid-migration, the app needs DDL rights in production, a failing migration crash-loops every replica (outage), and there's no rollback/review gate.
9. **Cost levers.** Scale-to-zero/min replicas for non-critical apps and dev environments; right-size CPU/memory per container and use consumption vs dedicated plans appropriately; Postgres Flexible Server tier (burstable for dev) + stop dev servers out of hours; Service Bus tier; log ingestion volume (sampling, retention, basic logs); reserved capacity/savings plans for steady production; tear down ephemeral environments.
10. **4 teams / 20 services platform.** Environments: dev (per-PR ephemeral where useful), test/staging (prod-like), prod, in separate subscriptions/resource groups. IaC modules shared and versioned by a platform team; each service has its own pipeline (build once → deploy to dev → automated tests → staging → manual/automated gate → prod with revisions/canary). Config per environment, secrets in Key Vault via managed identity, policy guardrails (Azure Policy), observability baked into templates, rollback = traffic shift + backward-compatible migrations. DORA metrics tracked.

**Aspire verdict (no single right answer):** a good ADR-016 says what Aspire does well (local orchestration as code, service discovery, dashboard, onboarding speed, generated deployment) and where you'd still want control (hand-tuned Bicep, existing platform standards, non-.NET services, production config). Then it decides per environment.
