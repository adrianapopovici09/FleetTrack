# M10 answers — Performance & caching

1. **Percentiles.** Averages hide the tail: a 50 ms average can coexist with 5% of users waiting 3 s. p95/p99 show what real users (especially heavy users making many calls) experience, and a page with 20 calls almost always hits someone's p99. **Coordinated omission:** a load tool that waits for each response before sending the next request backs off when the server is slow, so it under-reports latency during exactly the slow periods. Use constant-arrival-rate executors (k6 `constant-arrival-rate`) to measure correctly.
2. **"The API is slow" method.** Clarify: which endpoint, since when, for whom, what percentile vs the SLO? Reproduce with metrics/traces from production (find the slow spans: DB, external call, CPU, GC, lock waits). Form one hypothesis, profile (dotnet-trace/counters, EXPLAIN), change one thing, re-measure under the same load, record the result, and roll out with monitoring. Check recent deploys and config changes first.
3. **Cache patterns.** Cache-aside: the app reads the cache, on a miss loads from the DB and populates; simple and flexible, but stampede risk and the app owns the logic. Read-through: the cache layer loads on a miss (e.g. HybridCache's `GetOrCreateAsync`), centralised with built-in stampede control. Write-through: writes go to the cache and DB together, so the cache stays fresh, but writes are slower and the cache fills with data nobody reads. Write-behind: async DB writes, fast but risks data loss.
4. **Stampede.** A popular key expires (or the cache starts cold) and many concurrent requests miss simultaneously, all hitting the DB at once and possibly overloading it. HybridCache coalesces concurrent requests for the same key in-process: only one factory call runs and the others await its result (plus an L1/L2 combination). Also useful: TTL jitter, early refresh, locks for distributed coalescing.
5. **Versions/tags over deletes.** Deletes miss related keys (lists, aggregates, different variants), race with concurrent repopulation (a reader puts stale data back after your delete), and are hard across L1 caches on many instances. Versioned keys/tags invalidate a whole group atomically: bump the version and old entries simply become unreachable and expire. HybridCache's `RemoveByTagAsync` handles grouped invalidation.
6. **Cache key problems.** No tenant or user in the key → user-specific fields (and possibly other tenants' data) are served to the wrong people. 1 h TTL with no invalidation on update → stale for up to an hour. No jitter → mass expiry. Caching a DTO with user-specific fields in a shared cache defeats the purpose. Fix: tenant (and user, if personalised) in the key, invalidate on change via event/tag, separate shared vs per-user data.
7. **Caching as the wrong fix.** When the underlying query is just missing an index or is an N+1 (fix the root cause); when data must be strongly consistent (balances, inventory decisions); write-heavy data with low read reuse; highly personalised data with a low hit rate; when cache complexity and invalidation bugs outweigh the gain; when the bottleneck isn't reads at all.
8. **Little's law.** L = λ × W = 400 × 0.25 = **100 concurrent requests in flight**. If each request holds a DB connection for its whole duration, a pool of 100 is exactly saturated: any latency increase makes requests queue for connections, which increases latency further (a death spiral). Shorten connection hold times, add capacity headroom, or reduce per-request DB time.
9. **Output vs response caching.** Response caching sets HTTP cache headers and respects them; it's driven by client headers and caches in clients/proxies (and optionally a server middleware that obeys client `Cache-Control`). Output caching is a server-side cache configured by the app, independent of client headers, with policies, vary-by rules, tag-based eviction, locking (stampede protection) and pluggable storage (e.g. Redis).
10. **Flash sale, 50k RPS.** Serve the static product page from a CDN; separate static content (long-cached) from dynamic data (price/stock), which comes via a small API with a short TTL (1–5 s) in Redis + an in-process L1 and request coalescing. Pre-warm caches before the sale. Show stock as approximate ("in stock" vs exact counts), with the real reservation done in an atomic/queued checkout path. Rate-limit and use a queue/waiting room for checkout; scale out stateless nodes; load-test in advance.
