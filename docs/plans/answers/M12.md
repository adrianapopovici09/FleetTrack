# M12 answers — Observability

1. **Three signals.** Metrics: "is something wrong, and how much?" (cheap aggregates, alerting, trends). Traces: "where is it slow or failing in this request's path across services?" Logs: "what exactly happened, with details?" (events, errors with context). Correlated by trace id, so you go metric → exemplar trace → logs.
2. **Context across a broker.** The publisher injects the current trace context (W3C `traceparent`/`tracestate`) into message headers. The consumer extracts it and starts its processing span as a child of, or *linked* to, that context. Libraries (Wolverine, MassTransit, the RabbitMQ client instrumentation) can do it; otherwise inject and extract manually with OTel's propagator API.
3. **[LoggerMessage].** Source-generated: no string interpolation or boxing when the log level is disabled, no parsing of the template at runtime, structured parameters preserved as named fields (queryable), compile-time checks of the template and parameters, and stable event ids. Interpolation formats the string eagerly and loses structure.
4. **Cardinality.** The number of unique label combinations per metric. Each combination is a separate time series stored in the metrics backend. Unbounded labels (user id, shipment id, URL with ids) create millions of series: memory and storage blow up, queries slow down, costs explode, and the backend can fall over. Keep labels bounded (status code, route template, tenant tier).
5. **RED vs USE.** RED (Rate, Errors, Duration) for request-driven services/endpoints and consumers. USE (Utilisation, Saturation, Errors) for resources: CPU, memory, DB connection pools, thread pool, queue depth, disks.
6. **Error budget / burn rate.** The SLO (e.g. 99.5% success over 30 days) allows a 0.5% error budget. Burn rate = how fast you're consuming it (e.g. 14× means the month's budget will be gone in ~2 days). Multi-window burn-rate alerts page only for user-impacting, sustained problems. CPU > 80% is a cause, not a symptom: it may be fine (efficient use) or irrelevant to users, produces noise and alert fatigue, and misses failures that don't use CPU.
7. **Head vs tail sampling.** Head: decide at trace start (e.g. keep 10%); cheap and simple, but you may drop the rare error/slow traces you care about. Tail: decide after the trace completes (keep all errors and slow traces, sample the rest); keeps interesting traces but needs a collector buffering complete traces (memory, complexity, cost).
8. **Bad log line.** (1) String interpolation: allocations and loss of structured fields (can't query by shipment id). (2) `shipment` object interpolated: logs `ToString()` (useless or huge), may dump sensitive data. (3) **PII:** the customer email in logs (GDPR, retention, leaked via log access). Also no event id, and Information level may be wrong for high-volume paths.
9. **Every alert needs:** a clear user-facing symptom/SLO it protects, actionability (someone can do something now), a severity and owner/routing, a link to a runbook with first steps, and the dashboard/query links for context. No alert without a reason to wake someone.
10. **FleetTrack on Azure.** OTel SDK in all services → Azure Monitor (Application Insights via OTLP/distro) or an OTel Collector → Grafana Cloud/managed Prometheus. Traces with tail sampling at the collector (keep errors/slow ones), metrics (RED + domain), logs with PII scrubbing. Retention: traces ~7–14 days, logs 30 days (archive cheaper), metrics 13 months downsampled. Cost controls: sampling, log levels, cardinality limits, daily caps/budgets. SLO burn-rate alerts route to the on-call team via PagerDuty/Teams; dashboards per service + business; runbooks linked.
