# M11 answers — Security & multi-tenancy

1. **Code + PKCE vs client credentials.** Authorization code + PKCE is for user-facing apps (SPAs, mobile) where a user logs in. PKCE exists because public clients can't keep a client secret: the app sends a hashed one-time code verifier, so an intercepted authorization code is useless without the verifier. Client credentials is for machine-to-machine calls with no user (services, daemons), authenticating with a secret or certificate.
2. **JWT checks.** Signature (with keys from the issuer's JWKS, a pinned algorithm, never `alg: none`), issuer (`iss`), audience (`aud`), expiry/not-before with small clock skew, and required scopes/claims. Audience validation prevents a token issued for *another* API (same identity provider) from being replayed against yours, because a token for service A must not work on service B.
3. **BOLA.** Broken Object-Level Authorization: the API checks that you're authenticated and have the right role, but not that *this specific object* (shipment 1234) belongs to you, so changing the id in the URL returns someone else's data. Roles answer "can you call this endpoint type?", not "can you access this record?". You need resource-based checks (ownership/tenant) on every object access.
4. **404 vs 403.** 404 hides the object's existence (prevents enumeration/leaking that shipment 1234 exists): preferred for cross-tenant or cross-customer access. 403 is clearer for legitimate users who can see the object but lack the permission for an action (e.g. a customer viewing a shipment but not allowed to cancel it). Be consistent and document it.
5. **Tenancy models.** Shared schema + tenant_id: lowest cost and simplest operations, scales to many small tenants; weakest isolation (needs strong guardrails like RLS) and noisy-neighbour risk. Schema-per-tenant: moderate isolation and per-tenant customisation/restore; migrations multiply and it scales to hundreds, not tens of thousands. DB-per-tenant: strongest isolation, per-tenant scaling, residency and backup; highest cost and operational overhead. Often hybrid: shared for most, dedicated for large or regulated tenants.
6. **RLS plus filters.** Defence in depth: query filters live in the app and are bypassed by raw SQL, Dapper queries, `IgnoreQueryFilters`, a new developer's mistake, reporting tools or a compromised component. RLS enforces isolation in the database itself, so a forgotten filter returns nothing instead of leaking. Cost: performance considerations and session-variable management.
7. **Tenant from header.** The client controls headers, so anyone can set another tenant's id and impersonate it (a full cross-tenant breach). The tenant must come from the validated token (a claim issued by the identity provider), or from a server-side mapping of the authenticated principal. A header may at most *select* among tenants the token proves you belong to.
8. **Session-level SET on pooled connections.** Pooled connections are reused across requests and tenants. The setting stays from whoever last set it (or is never updated because "open" happens once per physical connection), so a request for tenant B may run with tenant A's id: a leak, or wrong results. Use `set_config('app.tenant_id', @t, true)` (transaction-local) per transaction/command, or reset on connection return, and test it with concurrency.
9. **Monolith → Tracking auth.** Use client credentials (its own service identity, audience = Tracking, minimal scopes), or token exchange when Tracking must know the user. Forwarding the user's token everywhere: the token's audience is the gateway/monolith, not Tracking (so either audience validation is weakened or it fails), it expands the blast radius if any service leaks it, services gain user-level power they don't need, and background jobs have no user token. Pass the user/tenant context explicitly and authorise at each service.
10. **Dedicated regional DB for one customer.** Tenant-aware data access: a tenant catalogue mapping tenant → connection string/region; the `DbContext`/connection factory resolves per request; migrations applied to every tenant database by the pipeline; messaging/caches keyed by tenant (possibly regional infrastructure). A migration path to move a tenant (export/import with downtime window, or replication). Pricing reflects the cost. RLS and filters remain as defence in depth.
