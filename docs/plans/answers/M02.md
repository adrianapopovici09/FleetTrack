# M02 answers — API design

1. **Keyset vs offset.** Offset makes the database read and discard N rows (cost grows with the page number), and inserts/deletes between requests shift rows, giving duplicates or gaps. Keyset uses `WHERE (created_at, id) > (@c, @i) ORDER BY ... LIMIT n`: an index seek of constant cost, stable under concurrent inserts. Offset is fine for small, mostly static data or when users need "jump to page 37".
2. **ETag/If-Match vs body version.** Both implement optimistic concurrency (reject the update if the resource changed). The header is standard HTTP: it works for any representation and with conditional GETs/caching (`If-None-Match` → 304), intermediaries understand it, and it keeps concurrency metadata out of the domain payload. 412 and 428 have defined semantics.
3. **412 / 409 / 428.** **412 Precondition Failed:** the `If-Match` ETag doesn't match the current version (someone else changed it). **409 Conflict:** the request conflicts with the resource's state or a business rule (illegal transition, duplicate). **428 Precondition Required:** the server requires a conditional request and the client sent no `If-Match`.
4. **Retry on POST.** Without a key, the first request may have succeeded server-side (the timeout happened on the way back), so the retry creates a *second* shipment: double booking and double billing. With a key, the server finds the stored record for `(tenant, key)`. If the body hash matches, it replays the original 201 response and nothing new is created. If the first attempt is still running, it returns 409/425 "in progress".
5. **Key scope and body hash.** Scope: keys are client-generated, so two tenants could pick the same one. Without tenant/user scope, one client could receive another's stored response (a data leak) or be blocked by it. Hash: detects a client reusing the key for a *different* request (a client bug). Replaying the old response for different data would silently lose the new request, so you reject it with 422/409.
6. **Breaking changes.** Adding a field is non-breaking for tolerant readers. Making an optional field required is breaking: old clients don't send it. Renaming is breaking (remove + add). **Adding an enum value** is breaking for clients that deserialize into a closed enum or use exhaustive switches: they crash or mis-handle the unknown value. Document that enums are open and clients must handle unknown values, or version the API.
7. **Check-then-insert.** A race: two concurrent requests both see "not exists" and both insert. You get duplicates, or one gets a unique-violation exception that isn't handled. Fix: a unique constraint on `(tenant, key)` and insert first (`INSERT ... ON CONFLICT DO NOTHING`, or catch the unique violation), treating a conflict as "already processed/in progress".
8. **Shape vs business validation.** "Body has a pickupDate of the right type" is shape/contract validation at the API edge (fast 400 with field errors). "Pickup before delivery" is a business invariant: it belongs in the domain (value object/aggregate) so it holds for *every* entry point (API, messages, AI tools, imports). It can be mirrored at the edge for UX, but the domain is the source of truth.
9. **Stable type URI.** A machine-readable, stable identifier clients can branch on (e.g. "insufficient-capacity" → show the alternative-vehicle UI). `title`/`detail` are human text that may change or be localised. Changing the `type` is a visible contract change.
10. **Partner API design.** Auth: OAuth2 client credentials per partner (or mTLS), scopes per capability. Idempotency-Key on all creates. URL versioning (`/v1`) with a written deprecation policy and `Sunset` headers. Keyset pagination for lists. Status updates via **webhooks** (HMAC-signed, retries with backoff, delivery log, replay) plus a polling fallback (`GET /shipments?updatedSince` with a cursor). Per-partner rate limits with `429 + Retry-After`, ProblemDetails errors, OpenAPI + SDKs, a sandbox environment, and contract tests in CI.
