# M03 answers — Data with EF Core & PostgreSQL

1. **timestamptz.** It stores an absolute instant (normalised to UTC). `timestamp` is a wall-clock value with no zone, so its meaning depends on who wrote it. Freight crosses time zones and DST changes: "pickup at 10:00" must be unambiguous for sorting, SLAs and ETAs. Npgsql maps `DateTime` (Kind=Utc) / `DateTimeOffset` to `timestamptz` and rejects non-UTC values, which is a good guardrail.
2. **Cartesian explosion.** Including two sibling collections in one SQL query joins them: rows = parents × stops × items, so data is duplicated massively over the wire. `AsSplitQuery` issues one query per collection. Pros: no duplication. Cons: multiple round trips, and the queries can see *different* snapshots if data changes between them, unless you use a transaction with suitable isolation. Ordering and paging need care too.
3. **Composite index usage.** Index `(tenant_id, status, created_at)`: filter by `status` only → generally **no** (the leading column is missing; Postgres may skip-scan in limited cases, but don't rely on it). `tenant_id` + `status` ordered by `created_at` → **yes, ideal**: equality on the first two columns, and the third gives order without a sort. `tenant_id` ordered by `created_at` → **partially**: it can use `tenant_id` for filtering, but the order is broken by `status` in between, so it needs a sort (or a separate `(tenant_id, created_at)` index).
4. **Partial index.** When queries target a small, well-defined subset. Example: `CREATE INDEX ... ON shipments (planned_delivery) WHERE status NOT IN ('Delivered','Cancelled')`. Active shipments are maybe 2% of rows, so the index is tiny and fast for "late shipments", and writes to delivered rows don't maintain it.
5. **BRIN vs B-tree.** BRIN stores min/max per block range: tiny and cheap to maintain, but effective only when the column's values correlate with physical row order (append-only time data like `recorded_at`). B-tree for random-access lookups, uniqueness, or uncorrelated columns. BRIN on a randomly ordered column is useless.
6. **ToList first.** `ToList()` materialises **the entire table** into memory, then filters and takes 10 in .NET. It should be `db.Shipments.Where(...).Take(10).ToList()`, so the filter and `LIMIT` run in SQL. Also: no ordering (so `Take` is nondeterministic), status as a magic string, probably tracked entities, and no projection.
7. **AsNoTracking.** It skips change-tracker snapshots and identity resolution: less memory/CPU, faster reads. It's a bug when you then modify those entities and call `SaveChanges` expecting updates (nothing is tracked, or you attach duplicates), or when you rely on identity resolution (the same row giving the same instance in a graph). Use it for read-only queries and projections.
8. **ExecuteUpdate consequences.** (1) Entities already loaded in the context are stale (the tracker isn't updated). (2) No domain logic, events, interceptors or `SaveChanges` hooks run (audit fields, domain events, concurrency tokens unless you include them), and it runs immediately, outside your `SaveChanges` unit of work unless you wrap both in an explicit transaction.
9. **xmin.** `xmin` is a Postgres system column holding the ID of the transaction that last wrote the row; it changes on every update. Mapped as a concurrency token, EF adds `WHERE id = @id AND xmin = @original` to UPDATE/DELETE. If 0 rows are affected, EF throws `DbUpdateConcurrencyException`, which you map to 412/409 or a retry.
10. **12 filters / 50M rows / <100 ms.** Profile real query patterns. Composite indexes for the top filter+sort combinations (equality first, then range/sort). Keyset paging. Always filter by tenant first. Partial indexes for active rows. Projections via Dapper. If the combinations explode: a denormalised read model/materialised view per screen, or a search engine (OpenSearch/Elastic, Postgres FTS + GIN) for free-text and multi-facet filtering. Archive old rows or partition. Measure with EXPLAIN; set an SLO.
