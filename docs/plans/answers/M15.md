# M15 answers — Architect's toolkit

1. **C4 levels.** (1) System context: the system as a box with its users and external systems, for everyone including non-technical stakeholders. (2) Containers: deployable/runnable units and data stores (gateway, monolith, Tracking service, Postgres, broker) and how they communicate, for architects, developers and ops. (3) Components: the major building blocks inside one container (modules, key services), for developers of that container. (4) Code: classes, rarely drawn, usually generated by the IDE.
2. **ADR useful two years later.** It captures the *context and forces* at the time (constraints, scale, team, deadlines), the real options considered with their trade-offs, the decision and its consequences including the negatives accepted, and a revisit trigger. It's immutable (superseded, not rewritten), dated, and linked to related ADRs. Future readers can tell whether the reasons still hold.
3. **Strangler fig.** Put a facade/proxy (e.g. YARP) in front of the legacy system; incrementally route individual capabilities to the new implementation while the rest still goes to legacy; when nothing is left, retire the old system. Biggest risks: shared data/state between old and new (dual writes, inconsistency, who owns which tables), and the migration stalling halfway, leaving two systems to maintain forever. Mitigate with a data-ownership plan and an explicit finish line.
4. **Incremental ASP.NET → Core migration.** Stand up an ASP.NET Core app in front (YARP proxying unknown routes to the legacy app); migrate endpoints one by one; use the System.Web adapters to share APIs; share authentication (remote app authentication or a shared cookie/identity provider) and session (remote session), so users don't notice; extract business logic into .NET Standard / multi-targeted libraries usable by both; migrate data access carefully (same DB at first). Shared during migration: authentication, session, the database, configuration and libraries.
5. **Characterisation tests.** Tests that capture the system's *current* behaviour (whatever it is, bugs included) by feeding inputs and recording outputs, often as snapshot/approval tests (Verify). Write them before refactoring or migrating legacy code without tests, so you can detect behavioural changes. Then decide deliberately which changes are bug fixes.
6. **Rewrite vs incremental.** Incremental is almost always safer: continuous value delivery, lower risk, learning as you go, and the business keeps running. A rewrite might be justified when the system is small enough to rewrite in weeks, the technology is truly dead (unsupported platform, no way to run it) and incremental bridging is impossible, or the domain/requirements have changed so fundamentally that little of the old behaviour is needed. Even then, use strangler-style cutover rather than big-bang.
7. **45-min design interview structure.** (1) Clarify requirements: functional, non-functional, scale (5 min). (2) Back-of-envelope estimates: QPS, storage, bandwidth (5 min). (3) API and data model (5–10 min). (4) High-level design diagram (10 min). (5) Deep dives on 1–2 critical components the interviewer cares about (10–15 min). (6) Bottlenecks, failure modes, trade-offs, monitoring and evolution (5 min). Think out loud and state assumptions.
8. **Presenting to non-technical stakeholders.** Start with the business problem and outcome, not technology; present 2–3 options with cost, risk, time and what each means for the business (customers, revenue, compliance); make a clear recommendation; use simple visuals (context diagram, timeline); quantify where possible; state what you need from them (decision, budget, priority) and the risk of doing nothing.
9. **Estimating under uncertainty.** Break the work down to the level where estimates are possible; time-box discovery/spikes to reduce the biggest unknowns first; give ranges (best/likely/worst, or confidence levels) instead of single numbers; use reference-class data from past migrations; add explicit buffers for known risk areas; plan in increments with checkpoints where the estimate is revisited; communicate assumptions.
10. **Bank, first 90 days.** Understand before changing: stakeholder interviews, map the business capabilities and current architecture (dependencies, data, batch jobs, integrations), measure (deploy frequency, incidents, hot spots in change history). Define target outcomes and principles (why cloud-native: cost, speed, resilience?). Quick wins: CI/CD, automated tests around critical flows (characterisation tests), observability, and infrastructure as code for the existing system. Pick a first, low-risk but meaningful capability to strangle out behind a gateway, to prove the path (including security/compliance sign-off). Plan the data strategy (batch jobs → events/streaming gradually). Produce a roadmap with incremental milestones, a governance/ADR process and team enablement.
